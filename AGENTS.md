## Technical Basis and Layout

- `Cargo.toml` / `Cargo.lock`: Rust 2021, `workers-rs` 0.8; do not infer a minimum Rust version. `package.json` / `package-lock.json`: Wrangler 4, used only as a development and deployment tool; installs reuse the lockfile.
- `wrangler.toml`: source of truth for routes, compatibility date, build, static assets, Cron and queue configuration; `worker-build --release` produces `build/index.js`, and `public/` is served by Workers Assets.
- `src/lib.rs`: only the Worker HTTP, Cron and queue event exports; `src/api.rs`: routing, JSON/form input validation and HTTP responses; `src/domain.rs`: shared domain data, the `UpdateAction` enum and pagination constants.
- `src/firmware/`: `mod.rs` is the unified per-brand query entry; `huawei.rs` / `honor.rs` keep separate brand requests and credentials; `manual.rs` / `remote_zip.rs` handle the three-package flow and ZIP Range reads; `fingerprint.rs` handles XML fingerprints.
- `src/storage/`: `Repository` is the single database entry; `mod.rs` handles connection and migrations, `firmware.rs` handles the firmware list, writes, historical fingerprints and refresh seed queries, `device_models.rs` handles the mapping sync transaction, and `neon.rs` handles Neon HTTP transport. SQL, transaction locks and query result parsing live in this directory.
- `src/service.rs`: the save flow shared by version submission, manual three-package submission and background refresh — verify the new XML, read and initialize historical fingerprints, then deduplicate and write; no database access before verification passes.
- `src/tasks/mod.rs`: Cron dispatch; `src/tasks/device_models.rs`: device model CSV download and validation; `src/tasks/firmware.rs`: refresh seed selection, queue enqueue/consume and Huawei update queries; `src/notifications.rs`: Telegram message construction, background push and direct send.
- Module boundaries: domain data is independent of HTTP and the database; firmware adapters do not access the database; the storage layer does not fetch XML, build HTTP responses or push notifications; the API and background refresh write through the shared save flow and notify only after success. When migrating callers, update references directly and remove old paths without compatibility forwarding.
- `migrations/`: idempotent SQL migrations; `public/index.html`, `public/app.js`, `public/style.css`: page, interaction and styles; `public/i18n.js`: zh/en/ru message dictionary and language switching, loaded before `app.js`. Pure page changes need no Rust changes.
- Huawei and Honor device credentials come from Worker secrets `HUAWEI_DEVICE_ID/HUAWEI_DEV_CERT/HUAWEI_KEY_ATT` and `HONOR_DEVICE_ID/HONOR_DEV_CERT/HONOR_KEY_ATT` (Honor credentials originate from `../honor_mock/app.py`); `DeviceCredentials` in `src/firmware/mod.rs` reads them per brand and passes them to `huawei.rs` / `honor.rs`; no credentials are embedded in source. When missing or empty, version submission returns 500 without requesting OTA or saving, and background refresh tasks fail and are retried by the queue. `../check_huawei_ota.py` is a read-only OTA investigation tool that does not read XML; it prints 「返回固件（未验证XML）」 ("firmware returned (XML not verified)") and never claims a version name is already recorded.

## API and Storage Contract

- `GET /`: static home page. `POST /requests`: accepts JSON / form, validates per `brand` (default `huawei`); saves only when firmware is available and XML verification passes. 201 on success, 409 duplicate, 422 no firmware, 502 XML verification failure; nothing is saved when there is no firmware or on network errors.
- Version submission requires `dev/base/cust/preload/upgrade_or_erec`; `brand` is only `huawei/honor`, `vendor` defaults to `all_cn`, and an empty or omitted `patch` means no patch is queried. `upgrade_or_erec` only accepts `upgrade` (incremental) / `recovery` (full).
- Package types for internal submissions, OTA requests and refresh seeds uniformly use `UpdateAction::Upgrade/Recovery`, parsed via `FromStr` and emitted as protocol values via `as_str()`; no internal package-type `String`, no legacy ACTION string constants. HTTP, OTA and the database keep using `upgrade/recovery`, and fixed SQL literals stay as-is; `emulater` is only used for list filtering and admin imports and is not part of the OTA action enum.
- Huawei calls `update-drcn.platform.hicloud.com/BL/v1/VersionCheck`; Honor calls `update.platform.hihonorcloud.com/blversion/v1/version/check` with its own certificate and request structure, parses the numeric `status` and the nested `result.checkResult/versionList/blVersionCheckResults`, excludes purely numeric version changelog entries, and never fabricates links for a missing PRELOAD.
- `POST /requests/manual`: JSON only, `{"urls":["package URL", "..."]}`, at most 16 KiB, extra fields rejected. 201 on success, 400 invalid input, 415 non-JSON, 413 too large, 422 package validation failure, 502 XML verification failure, 409 duplicate; the success response has the same shape as version submission.
- `GET /requests`: merges both brands with no brand filter. Returns `{ requests, total, page, perPage }`; each record has `id/brand/dev/vendor/targetBlVersionNumber/deviceName/created_at/upgrade_or_erec/packages[]`, ordered by `id` descending.
- List parameters: `page` starts at 1, default 1, 50 per page; `q` fuzzy-matches device, channel, target version, package version number and Chinese model name; a valid `action=upgrade/recovery/emulater` restricts the package type first. Without a valid `action`, emulators are excluded by default and only mixed in with `include_emulators=1`; search and filters apply before pagination and counting.
- `firmware_submissions` stores brand, device, submission parameters, target version and time; `firmware_packages` stores only `versionNumber` and URL per package, never the raw upstream response. OTA URLs are completed to `<directory>/full/filelist.xml`; manual three-package and emulator records keep direct ZIP links. Historical data and admin imports that omit the brand default to Huawei.
- `lgrp_num` is a stored generated column computed from `base`, supporting multi-digit numbers, e.g. `GEM-LGRP3-CHN 207.0.0.100(SP10)` → `LGRP3`; `NULL` when no complete number is present. Writes omit this column and must never override it; historical and future `base` changes sync automatically.
- Emulators always use `upgrade_or_erec=emulater` (keep this spelling), `vendor` is only `arm64/x86`, and only admins may import them with database credentials. The public version API returns 400 for JSON / form emulator submissions without requesting OTA or saving.

## XML Fingerprints and Historical Data

- Version submission, manual three-package submission and scheduled refresh share XML content deduplication. The real `filelist.xml` is read, normalized and hashed with SHA-256, stored as `xml:v1:<64 hex chars>`; the `(brand, content_key)` unique index prevents concurrent duplicates and isolates brands.
- Fingerprint fields: `spath/dpath/operation/sha256/size` of `files/file`, `shainfo/size/subpath/package` of cloud packages, `filename/sha256/size` of extension packages. Formatting, entry order, checksum case and numeric leading zeros are ignored; package grouping and duplicate counts are preserved.
- Version names, download URLs, signatures and other XML metadata are not part of the fingerprint; file changes under the same version can be saved, while a changed URL or name alone returns 409 "An identical package already exists". Huawei purely numeric version entries are changelogs: excluded from the fingerprint, and their pseudo-XML links are never requested.
- The historical migration only clears old version-name signatures and keeps firmware. On submission, only old records of the same brand and target version without a baseline are located, and their old XML is read and compared; names are used only for locating. Records with an established baseline are deduplicated across version names within the same brand; baseline-less records of other target versions are not scanned database-wide.
- When historical XML is gone or invalid, the record is kept and its ID logged, with no blocking by version name, so unverifiable old packages may be saved again. Without a historical XML snapshot, content replaced in place upstream cannot be recovered.
- When a newly submitted XML is non-200, redirected, or has invalid format or fingerprint fields, 502 is returned with no save and no notification, and no fallback to version-name or URL deduplication. Only the brand's trusted CDN hosts are allowed; credentials, ports and redirects are forbidden; UA is `curl/8.13.0`; each XML is streamed with a 1 MiB limit; at most 32 OTA entries per request.
- Fingerprints rely on checksums declared in the XML; full firmware is never downloaded, and there is no claim of verifying the full ZIP SHA-256 or upstream signatures.

## Manual Three-Package Security Boundary

- Accepts 3 required packages plus an optional 4th updater, in any order. Each is first checked with `starts_with("http://update.dbankcdn.com/")`, then the URL is parsed; at most 2048 bytes, and it must be a direct ZIP link under `full/`. HTTPS, other hosts, credentials, ports, query strings, fragments, percent-encoding, backslashes, path traversal and duplicate package types are rejected.
- File names are restricted to `update_full_base.zip`, `update_full_cust_<model>_<channel>.zip`, `update_full_preload_<model>_<channel>_R<version>.zip` and an optional `updater.zip`; CUST/PRELOAD model and channel must match.
- `VERSION.mbn` is read via HTTP Range, supporting ZIP64 and stored/deflate. First request `bytes=0-0`, strictly validate `Content-Range` to get the total length, then compute explicit start/end ranges; `bytes=-N` is forbidden because some CloudFront nodes ignore suffix ranges and return the whole package with 200.
- Package type, model/series, C region code and the PRELOAD R version must match the file names; the channel comes from the matched file name, E/P come from the last segment of the CUST/PRELOAD numeric versions, whose version prefix need not match BASE. The full version is reassembled by reversing the frontend parsing algorithm, e.g. `BRE-AL80-LGRP9 207.0.0.111(SP10C00E111R1P2)`.
- A full three-package set is always saved as `recovery` (full package); an optional updater does not change the classification. The updater's `update.tag` is read and strictly validated for `PKG_UPDATE_MODE=OTA`, `PKG_TYPE=PATCH`, `PKG_DATA_TYPE=FULL`, rejecting duplicate or unknown fields. Its label is saved as `updater.zip`, never a fabricated `patch00` or target patch number; the tag cannot prove the updater is version-bound to the three packages.
- Downloads forbid redirects and require 206, an exact and consistent `Content-Range`, and no transfer compression; responses are streamed and cancelled when over limit. ZIP directory, local headers, entry boundaries, exact uncompressed size and CRC32 of the read entry are validated; duplicate same-name targets, encryption, multi-disk archives and corrupt data are rejected. There is no claim of verifying unread content or whole-package signatures.
- Per ZIP: at most 6 requests and 6 MiB downloaded; directory at most 4 MiB / 16384 entries; target compressed and uncompressed sizes limited to 1 MiB each. Then `filelist.xml` in the same directory is read and only the `file` entry uniquely matching the ZIP file name is fingerprinted, excluding unrelated files; three-package and four-package (with updater) sets keep distinct compositions. The database is accessed only after both version and fingerprint verification pass.

## Frontend Interaction Constraints

- The submission brand defaults to Huawei and only switches the submission route. Both brands share the firmware list, pagination, search and filters; switching brand does not refresh the list or reset the page, search, expanded details or the emulator toggle.
- "Submit a new version" has two native disclosure-triangle sections: "Submit by version" is expanded initially and on every brand switch, and can still be collapsed manually; "Submit three packages manually" is collapsed by default, contains only the URL input and submit button with no extra description or submit-area divider, and is hidden in Honor mode.
- Both brands show `auto-parse`, sharing the full-version splitting algorithm including model and LGRP, with examples switching per brand. The Honor example `WKL-AN80-LGRP1 11.0.0.111(SP7C00E110R101P2)` fills device and BASE/CUST/PRELOAD; parsing does not change the patch toggle. Honor has no patch by default; each brand keeps its own patch toggle state within the page session, and the field is omitted when unchecked.
- The header has "Haucet" and "Pedal(Beta)" (`https://github.com/ljlVink/Pedal`) in the navigation, then `.header-actions` holding a GitHub brand icon link (`https://github.com/ljlvink/FirmwareFetcher`, accessible name "GitHub"), a Telegram brand icon link (`https://t.me/firmwarefetcher`, Simple Icons path, accessible name "Telegram"), the language selector and the theme toggle; all links open in a new tab. GitHub, Telegram and the theme toggle share the 36px bordered `.icon-button` style. The language selector is a visible native `<select>` with a Material `mdiTranslate` icon inside on the left, sharing height, radius and option colors with the brand `<select>`. On narrow screens the brand and navigation links share the first row, and all four `.header-actions` controls form one right-aligned row below, with individual link text kept intact.
- UI languages are `en/zh/ru`: `localStorage.lang` takes precedence, otherwise the primary subtag of `navigator.languages` is matched in order, falling back to English when nothing matches; a manual switch writes `localStorage.lang` and updates `<html lang>`. Static text is marked with `data-i18n` / `data-i18n-placeholder|title|aria-label`, dynamic text is produced via `t()`; switching language immediately re-renders the list, pagination and current notice without refetching. Backend error messages are English and shown as-is without translation. Quoted UI labels in this file are the English strings.
- List columns are Device, VENDOR, full firmware version `targetBlVersionNumber`, package type, and an expand-details control; `deviceName` is shown in small text under the device model code and hidden when there is no match; details contain each package's download link and the submission time. Regular types are only "Incremental" and "Full"; component PATCH markers never create a whole-package patch type.
- Emulator badges are "ARM64 Emulator" and "X86 Emulator", styled the same as Full in both dark and light themes. "Show emulator packages" to the right of "Firmware list" is unchecked by default; toggling returns to page 1, keeps search and package type filter, and sends `include_emulators=1` when checked.
- Honor "View XML" uses a native HTTPS link with `target="_blank" rel="noopener noreferrer"` pointing directly to the original `full/filelist.xml`. Users are told that on 403 they should set the UA for `update.hihonorcdn.com` to `curl/8.13.0` via a browser UA extension; downloads need the same UA.
- A web page cannot change the UA automatically; the frontend does not read, parse or proxy manifests cross-origin, no manifest API accepting client-supplied upstream URLs is added, and `no-cors` is not used to fake success. The CDN samples have no `Access-Control-Allow-Origin`; curl succeeding with an Origin header does not mean a web page can read it; direct navigation needs no site JS read permission. The backend reads manifests only during submission verification and historical baseline initialization, unaffected by browser CORS; when the CDN rejects Workers egress it explicitly returns 502.

## Scheduled Tasks and Device Model Mapping

- In `wrangler.toml`, `0 16 * * *` is the daily Huawei OTA refresh at 00:00 Beijing time and `0 0 * * *` is the device model sync at 08:00; dispatch is by trigger expression and an unknown expression fails the task. Changing Cron or the matching code requires redeployment; upstream data updates take effect on the next sync.
- `src/tasks/device_models.rs` is invoked through the unified Cron scheduler and downloads [MobileModels-csv/models.csv](https://raw.githubusercontent.com/KHwang9883/MobileModels-csv/main/models.csv), keeping Huawei/Honor China and global sources, multiple names and version variants, deduplicated by the four-column primary key; it reuses `NEON_CONN_STRING` and needs no external scheduler, new secret or extra migration.
- The database is initialized and synced only after the CSV is fully validated; the first Cron run can also create tables via migrations. HTTP failure, missing columns, duplicate columns, bad rows, mismatched source brand, NUL characters, or a missing brand all fail the task without touching the database.
- The Neon HTTP batch transaction holds the same transaction-level lock as 003, only adds missing mappings and deletes `huawei_*` / `honor_*` mappings removed or corrected upstream; other sources and all firmware and links are kept. Any failed step rolls back, and repeating the same snapshot adds and removes 0; the success log includes the valid count, added/removed counts and per-source counts, and errors propagate to the Cron failure state, visible in Workers Logs and scheduled execution history.
- Model display and name search share the `names` CTE in `LIST_SQL` (`src/storage/firmware.rs`); codes are compared case-insensitively with any `HUAWEI ` prefix stripped, and only the best-ranked tier is used, with ties joined by ` / `. Tiers in order: exact code (cross-brand allowed, same brand first, e.g. Huawei-submitted `OXF-AN10` → 荣耀 V30 PRO); submitted code one trailing character longer (`MNA-AL00A` → `MNA-AL00`); table code one trailing character longer (`KLE-AL00` → `KLE-AL00U`); explicit `CN` suffix (`NIZ-AL00CN` → `NIZ-AL00`); same-brand same prefix family before `-` (`TGR-W20` → `TGR-W00/W10`). Non-exact tiers are same-brand only. Within the family tier, rank by identical network letters, then same first letter, then any, then smallest numeric distance; `*_cn` sources win remaining ties. Emulator categories (no `-`) never match a family.
- Only the Worker sync implementation is maintained; the old Python sync script and `npm run sync:models` have been removed.

## Telegram Notifications

- After Huawei/Honor version submission or manual three-package submission is saved, `schedule` in `src/notifications.rs` with `Context::wait_until` sends one notification per new firmware; background refresh reuses `send` for direct sending and keeps queue rate limiting. English title, field names and package types, plain text, previews disabled, containing only brand, model, channel, target version and package type, with no links or bot signature.
- Duplicates (including unique index conflicts), verification/write failures, model sync and admin direct SQL imports never notify. Notifications are best effort: missing config, network failure, non-200 or API `ok:false` only log a redacted error, never block the HTTP success, roll back, auto-retry or resend.
- Configure `TG_GROUP` (channel/supergroup username, optionally with `@`, or numeric chat ID) and `TG_BOT_KEY`; the bot needs posting or messaging permission. The token is backend-only, stored as a secret, and never enters the frontend, logs or the repository.

## Database Migrations and Deployment Risks

- The connection string is configured as `NEON_CONN_STRING`, currently sourced from `../remote_neondb`; SQL is sent only through `src/storage/neon.rs` to `https://api.<region>.aws.neon.tech/sql` with the `Neon-Connection-String` header; no Postgres client crate is needed.
- On first database access the Worker runs idempotent migrations in order: 001 creates tables and migrates old data; 002 brand default, constraints, `content_key` and old index removal; 003 device model table, seeding 1586 Huawei rows into an empty table; 004 emulator and architecture constraints, correcting early whole-package `patch` to `recovery` while keeping links. 001/002 never delete, merge firmware or backfill signatures by the old five-tuple or version name.
- 005 adds the `lgrp_num` stored generated column under the firmware table migration lock; once the migration runs, existing Worker and admin writes generate it automatically with no separate write-logic change or deployment.
- 006 reuses the firmware migration lock, allows baseline-less `content_key=NULL`, only clears non-XML signatures, and keeps historical rows, the `(brand, content_key)` unique index and the historical query index; repeated cold starts do not rewrite XML fingerprints. Deploy the new Worker together with the revised 002/006 to avoid switching dedup rules while an old Worker keeps writing.
- Keep the `firmwarefetcher.ljlvink.top/*` route and `keep_vars = true` so deployment does not remove dashboard variables. Local `.dev.vars` is not uploaded automatically; reuse online variables/secrets of the same name, and do not create a secret when a text variable of the same name already exists. Deploying and changing secrets each require user authorization.
